# PortMatch 단일 EC2 측정 기록

EC2 한 대에 Spring Boot 1개, PostgreSQL 17 1개, Redis와 RabbitMQ를 두었다. RAM은 913 MiB, 스왑은 2 GiB였다. EC2 내부 결과는 k6와 앱이 같은 호스트의 자원을 공유한다. 부하 각 단계는 3분이었다.

## HTTP 요청률 탐색

공고 목록 `/api/job-postings/latest`와 제목 검색 `/api/job-postings/search`를 번갈아 호출했다. 이는 페이지네이션 화면 흐름과 별개의 워크로드다.

| 목표 RPS | 읽기 성공 RPS | 읽기 p95 | 읽기 누락 | 혼합 성공 RPS | 혼합 p95 |

| 5 | 4.82 | 75 ms | 25 | 5.01 | 63 ms |

80 RPS에서는 실제 전송 13,004건 중 256건(1.97%)이 5초 타임아웃이었다. 종료 직후 readiness 타임아웃으로 혼합 단계는 중단했다. 읽기·혼합 2 RPS는 별도 기준선 실행에서 세 번씩 통과했다. 위 표의 증량 구간은 각 단계 한 번 관측한 결과다.

## 화면 흐름과 페이지네이션

기존 `7acfe74` 전체 목록은 5천 건·10만 건 두 DB 모두 단일 HTTP 요청에서 10초 타임아웃이었다. `8f221f0`에서 페이지네이션으로 바뀐 첫 페이지는 각각 201 ms와 2.18초에 응답했다. 5천 건 데이터에서는 한 기업에 모든 공고가 들어 있어 상세의 동일 기업 공고 조회가 전체 5천 건을 읽는 특성이 있다. 10만 건 데이터는 기업당 10건이다.

10만 건만 다시 확인했을 때 첫 목록은 1.79초였다. 키워드 `0042`로 공고 검색과 기업 검색을 병렬 호출한 단일 흐름에서 공고 검색은 7.95초에 성공했고 기업 검색은 10초 타임아웃이었다. 증량은 실행하지 않았다.

별도 PostgreSQL 실행 계획에서 공고 제목 부분 검색은 최신순 기본 키 탐색으로 첫 20건을 찾기 전 39,939건을 걸러냈으며 6.77초가 걸렸다. 총 결과 50건을 계산하는 검색 count는 10만 건을 검사해 0.77초가 걸렸다. 이 SQL 측정은 위 HTTP 실행과 별도의 표본이다. 제목 GIN trigram 인덱스와 검색 연산자 변경은 후속 개선 후보로 논의했다.
