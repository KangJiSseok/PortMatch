# 동시성 DB

보통 이렇게 부른다 
- Client-side Database

- Offline-first Database

- Sync-based Database

- Conflict-free Replicated Data Store (CRDT)

- Collaborative / Real-time Sync DB

핵심 특징 한 줄 요약:

각 클라이언트가 자기 로컬 DB를 가지고 쓰고, 나중에 서버와 “동기화(sync)” 하면서 충돌을 해결한다


### 왜 이런 DB가 등장했나

전통적인 구조:

```
Client → API → Server → DB
```

문제:

1. 네트워크 끊기면 못 씀

2. 동시 수정 시 서버 락/트랜잭션 복잡

3. 실시간 협업(구글 Docs 같은 거) 구현 어려움

그래서 나온 구조:

```
Client (Local DB)
   ↕ Sync
Server (Sync Hub);
```

-> 동시성 문제를 서버 락이 아니라 “데이터 병합”으로 해결

## 핵심 기술 ① CRDT (진짜 중요)

CRDT란: 어떤 순서로, 몇 번 적용해도 최종 상태가 항상 동일해지는 자료구조

## 핵심 기술 ② Offline-first + Sync Log

클라이언트는:
1. 로컬 DB(SQLite, IndexedDB 등)에 먼저 씀
2. 변경 사항을 operation log 로 기록

서버는:
1. 로그를 모아서
2. 다른 클라이언트에 전파

충돌이 나면?
1. 미리 정의된 규칙으로 자동 병합 또는 사용자에게 선택권 제공

## 한 문장 요약
클라이언트 동기화 DB는 각 클라이언트가 로컬 DB를 소유하고 변경 로그를 동기화하며, 락 대신 CRDT 기반 병합으로 동시성 문제를 해결하는 구조다.




# HTTP Method — POST, PUT, PATCH의 차이와 멱등성

1. HTTP 메서드는 단순 전송 방식이 아니라 요청의 의미(semantic) 를 정의한다.

2. 멱등성이란 같은 요청을 여러 번 보내도 최종 서버 상태가 동일한 성질이다.

3. POST는 서버에게 처리를 위임하므로 반복 요청 시 결과가 누적될 수 있다.

4. 따라서 POST는 기본적으로 멱등하지 않다.

5. PUT은 리소스를 “이 상태로 만들어라”라고 최종 상태를 선언한다.

6. 같은 PUT 요청을 여러 번 보내도 결과 상태가 같아 멱등성이 보장된다.

7. PATCH는 현재 상태를 기준으로 부분 변경 연산을 적용한다.

8. PATCH는 증가·추가 같은 연산을 허용해 결과가 누적될 수 있다.

9. 그래서 PATCH는 스펙 차원에서 멱등성을 보장하지 않는다
