# [TIL] Docker 네트워크 통신: 서로 다른 네트워크의 컨테이너는 어떻게 연결할까?

## 1. Docker 네트워크의 대전제 (Golden Rule)
Docker 네트워크의 핵심은 **격리(Isolation)**와 **DNS**다.

> **"같은 Docker 네트워크에 속한 컨테이너끼리만 이름(DNS)으로 통신할 수 있다."**

- **같은 네트워크:** `http://컨테이너이름:포트` 로 통신 가능 (Docker 내부 DNS가 IP로 변환)
- **다른 네트워크:** 기본적으로 **통신 불가** (서로의 존재를 모름, IP 접근 불가)

<br>

## 2. 주요 네트워크 모드 3가지
실무에서는 주로 `bridge`를 사용한다.

1. **Bridge (Default):** 가상 브리지를 생성해 컨테이너마다 내부 IP를 할당. 같은 브리지 내에서는 DNS 통신 지원.
2. **Host:** 호스트의 네트워크 환경을 그대로 사용. 포트 바인딩 없이 호스트 포트 점유. (격리성 낮음)
3. **None:** 네트워크 인터페이스 없음. 완전 차단.

<br>

## 3. 문제 상황: 서로 다른 네트워크 간 통신
서로 다른 네트워크(`Net A`, `Net B`)에 있는 컨테이너는 보안상의 이유로 기본적으로 차단되어 있다.


## 4. 해결 방법 (Best Practice 순서)

### 🥇 방법 1: 설계 단계에서 같은 네트워크로 묶기 (권장)
애초에 통신이 필요한 서비스들은 `Docker Compose` 등을 통해 하나의 사용자 정의 네트워크(User-defined bridge)에 묶는 것이 가장 깔끔하다.

```yaml
services:
  app:
    networks:
      - my-network
  db:
    networks:
      - my-network
networks:
  my-network:
```

### 🥈 방법 2: Gateway 컨테이너 활용 (Multi-Network Connection)
특정 컨테이너(예: Nginx, Gateway)가 **양쪽 네트워크에 모두 다리를 걸치는 방식**이다.

- **원리:** 하나의 컨테이너는 여러 네트워크에 동시에 소속될 수 있다 (`docker network connect`).
- **구조:**
  - `Nginx`: Network A의 IP + Network B의 IP를 동시에 가짐 (NIC가 2개인 것처럼 동작)
  - `App A (Net A)` → `Nginx` → `App B (Net B)` 중계 가능
- **핵심:** 개발자가 "어느 네트워크로 보내라"고 지정할 필요가 없다. Docker 라우팅 테이블이 목적지 DNS/IP를 보고 자동으로 적절한 네트워크 인터페이스를 선택해서 내보낸다.



### 🥉 방법 3: 호스트 경유 (Port Binding + Host IP)
컨테이너끼리 직접 통신하지 않고, **호스트(Host)**를 찍고 다시 들어가는 방식이다.

- **설정:** 타겟 컨테이너가 포트를 호스트에 노출(`-p 8080:8080`)해야 함.
- **호출:** `http://host.docker.internal:8080` (또는 호스트 IP)
- **단점:** 네트워크 격리가 무너지고, 불필요하게 호스트 네트워크 스택을 탄다. 운영 환경보다는 **로컬 개발/디버깅용**으로 적합.
- **참고:** `host.docker.internal`을 쓰려면 `extra_hosts` 설정이 필요할 수 있음.


## 5. 핵심 요약 & 결론

1. Docker 컨테이너는 같은 네트워크에 있어야만 이름으로 편하게 부를 수 있다.

2. 네트워크가 분리되어야 한다면 Nginx 같은 중계 컨테이너를 두 네트워크에 모두 연결하는 것이 정석이다.

3. host.docker.internal을 이용한 호스트 경유 통신은 개발 환경에서의 임시 방편으로 생각하자.

4. 가장 좋은 건 처음부터 설계를 잘해서 같은 네트워크(Docker Compose)로 묶는 것이다.
