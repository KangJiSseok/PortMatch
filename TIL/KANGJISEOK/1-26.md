# 📌 TIL – SSH Reverse Tunnel에서 `0.0.0.0` 바인딩이 왜 Docker 컨테이너 접근을 가능하게 했는가

## 🧩 상황

EC2 서버에서 실행 중인 Docker 컨테이너(Portfolio Analysis 서비스)가
**로컬 PC에서 실행 중인 Docker 서비스(MinerU API)** 로 요청을 보내야 했다.

로컬 PC는 공인 IP가 없고, 포트 포워딩도 불가능했기 때문에
일반적인 네트워크 연결 방식으로는 EC2 → 로컬 접근이 불가능한 상황이었다.

이를 해결하기 위해 **SSH Reverse Tunnel (`-R`)** 방식을 사용했다.

---

## 🔍 시도한 두 가지 SSH 명령

### ❌ 동작하지 않았던 명령

```bash
ssh -i key.pem -N -R 18000:127.0.0.1:18000 ubuntu@ec2
```

### ✅ 동작했던 명령

```bash
ssh -i key.pem -N -R 0.0.0.0:18000:127.0.0.1:18000 ubuntu@ec2
```

겉보기에는 `0.0.0.0` 유무만 다른 것처럼 보였지만,
**실제로는 EC2에서 포트를 여는 방식 자체가 달라졌다.**

---

## 🔑 핵심 차이 – 포트 바인딩 위치

### 1️⃣ 기본 `-R` 옵션의 동작 방식

```bash
ssh -R 18000:127.0.0.1:18000 ...
```

위 명령은 실제로 다음과 동일하게 동작한다.

```text
EC2 서버의 127.0.0.1:18000 에만 포트를 오픈
```

즉:

* EC2 **호스트의 localhost** 에만 포트가 열림
* Docker 컨테이너의 `localhost`는 **EC2 호스트의 localhost와 다름**

👉 결과적으로 **컨테이너에서 접근 불가능**

---

### 2️⃣ `0.0.0.0`를 명시했을 때의 동작

```bash
ssh -R 0.0.0.0:18000:127.0.0.1:18000 ...
```

이 경우 SSH 데몬은 다음과 같이 동작한다.

```text
EC2 서버의 모든 네트워크 인터페이스에 대해 18000 포트를 오픈
- lo (127.0.0.1)
- eth0 (사설 IP)
- docker0 (Docker 브리지)
```

👉 그 결과:

* Docker 컨테이너에서도
* EC2 호스트 IP를 통해
* `18000` 포트에 접근 가능

---

## 🔄 실제 통신 흐름 정리

### ❌ 첫 번째 시도 (실패)

```text
[Docker 컨테이너]
   → localhost:18000  ❌
   → (EC2 호스트의 localhost 아님)
```

### ✅ 두 번째 시도 (성공)

```text
[Docker 컨테이너]
   → EC2_HOST_IP:18000
   → (SSH Reverse Tunnel)
   → 로컬 PC :18000 (MinerU API)
```

---

## 🧠 중요한 깨달음

### ✔️ 터널링은 “통신”이 아니라 “경로 설정”이다

* SSH Reverse Tunnel은

  * 특정 포트에 대해 **연결을 전달(forward)** 해주는 역할만 함
* 실제 연결이 발생한 이후에는:

  * HTTP / TCP 통신이
  * **일반 포트 통신과 동일하게 동작**

👉 컨테이너는:

* SSH를 인식하지 못하고
* 암호화 여부도 모르며
* 단순히 EC2의 열린 포트로 TCP 연결을 시도할 뿐

---

## ✨ 한 문장으로 정리

> `0.0.0.0`로 바인딩된 SSH Reverse Tunnel은
> EC2에서 일반 TCP 포트를 연 것과 동일하게 동작하며,
> Docker 컨테이너는 이를 **그냥 통신 가능한 포트**로 인식한다.

---

## 🔒 추가로 배운 점 (보안 관점)

* 이 방식은 **임시 테스트 / 개발 환경**에 적합
* 로컬 PC가 꺼지면 통신 즉시 불가
* `0.0.0.0` 바인딩은 외부 접근 가능성이 있으므로 주의 필요
* 실서비스 환경에서는 VPN, 전용 서버, Cloudflare Tunnel 등 대안 필요

## 배포 유저와 접속 유저가 달라 헷갈림

SSH로 접속한 ubuntu 유저에서
docker-compose.prod.yml 파일이 없다는 에러가 발생했다.

#### 원인 3 – GitLab Runner 유저 분리
CI/CD는 gitlab-runner 유저 기준으로 동작하고 있었고,
실제 배포 파일들은 다음 경로에 있었다.

```
/home/gitlab-runner/deploy
```
ubuntu 유저에서는 접근 권한도 없고, 파일도 보이지 않는 게 정상
