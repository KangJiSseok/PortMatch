## Docker 환경 크롤러 자동화 및 Spring JPA 최신순 조회 최적화

실제 배포 환경(Linux + Docker)에서 발생하는 **크론탭 경로 에러**를 해결하고, 백엔드(Spring Boot)에서 최신 데이터를 효율적으로 불러오기 위한 **페이징 및 정렬 로직**을 최적화했다.

---

## 1. 구현 내용: 자동화 스크립트 및 백엔드 API 정제
### 데이터 흐름 최적화
- **크론탭 경로 명시**: `cd` 명령어를 사용하여 작업 디렉토리를 확보함으로써 Docker 설정 파일(`.env`, `yml`) 로드 문제 해결.
- **Query Method 활용**: `findAllByOrderByIdDesc`를 통해 별도의 SQL 작성 없이 DB의 최신 데이터를 가져오도록 구현.

### 핵심 성과
- **자동화 안정성**: 매일 정해진 시간(UTC 07:50 / KST 16:50)에 크롤러가 최신 코드로 자동 빌드 및 실행되도록 설정.
- **조회 성능 최적화**: `Pageable`을 적용하여 대량의 공고 데이터 중 필요한 만큼만 최신순으로 끊어서 응답 가능.

## 2. 주요 트러블슈팅

### 🚨 Issue 1. 크론탭 실행 환경 변수 로드 실패
- **현상**: 크론탭을 통해 실행 시 `.env` 파일을 찾지 못해 컨테이너 설정이 깨지는 현상 발생.
- **원인**: 크론탭의 기본 실행 위치가 프로젝트 폴더가 아니기 때문에 상대 경로로 지정된 설정 파일들을 참조하지 못함.
- **해결**: 명령어 앞에 `cd /home/ubuntu/deploy &&`를 추가하여 명시적으로 경로를 이동시킨 후 명령을 수행하도록 수정.

---

### 🚨 Issue 2. DB 저장 순서와 사이트 노출 순서의 불일치
- **현상**: 크롤러가 최신 공고부터 긁어오지만, DB ID는 들어온 순서대로 부여되어 `ASC` 정렬 시 옛날 데이터가 먼저 보임.
- **원인**: DB의 Auto Increment 특성상 나중에 들어온 데이터(최신)가 항상 큰 ID를 가짐.
- **해결**: 
  - Repository에서 `ORDER BY id DESC` (내림차순) 정렬을 기본으로 설정.
  - 더 정확한 정렬을 위해 공고 시작일(`startDate`)을 기준으로 하는 복합 정렬 로직 고려.

## 3. 핵심 개념 정리

### 왜 크론탭에서 절대 경로와 cd가 중요할까?
크론탭은 아주 제한적인 환경 변수 내에서 동작하며, 사용자가 로그인했을 때의 쉘 환경과 다르기 때문이다.

### 오름차순(ASC) vs 내림차순(DESC)의 선택
- **오름차순**: 1, 2, 3... 순서로 데이터가 쌓인 순서 그대로를 보여줄 때 적합.
- **내림차순**: 최신 공고, 최근 게시글 등 사용자가 가장 궁금해할 '따끈따끈한' 정보를 상단에 배치할 때 필수적임.

### Repository 계층의 역할
서비스 단에서 복잡한 비즈니스 로직을 처리하기 전, DB로부터 데이터를 **어떤 순서(Sort)**로 **얼마만큼(Paging)** 가져올지 결정하는 문문 역할을 수행한다.
