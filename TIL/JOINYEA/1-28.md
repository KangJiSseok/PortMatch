# 📝 \[TIL\] 2026-01-28: JPA Entity ID 타입 변경 및 DB Identity 전략 적용 트러블슈팅

오늘은 채용 공고 시스템의 확장성을 위해 **Entity의 ID 타입을 String에서
Long으로 변경**하고,\
**데이터베이스의 자동 증가(IDENTITY) 전략을 적용**하는 전 과정을
진행했다.\
JPA와 DB 간의 타입 불일치 및 시퀀스 동기화 문제를 해결하며 **영속성
컨텍스트의 동작 원리**를 깊이 이해했다.

------------------------------------------------------------------------

## 1. 구현 기능: 채용 공고 및 기술 스택 저장 로직 개선

### 구조

    JobPosting (1) ↔ PostingStack (N) ↔ TechStack (1)

### 핵심 변경 사항

-   모든 엔티티의 ID 타입을 **String → Long**으로 변경
-   `@GeneratedValue(strategy = GenerationType.IDENTITY)` 적용으로
    **DB에 ID 생성 위임**
-   Flyway(V4)를 통한 **기존 테이블 스키마 및 데이터 타입 마이그레이션**

------------------------------------------------------------------------

## 2. 주요 트러블슈팅

### 🚨 Issue 1: 데이터 타입 불일치 (Operator Error)

**현상**\
ID를 Long으로 바꾼 후 조회 시

    operator does not exist: bigint = character varying

오류 발생

**원인**\
Java 코드는 `Long`인데, PostgreSQL 테이블의 ID 컬럼이 여전히 `VARCHAR`\
→ DB 레벨에서 비교 연산 불가

**해결**\
Flyway SQL 파일에서 명시적 형변환 수행

``` sql
ALTER TABLE job_postings 
ALTER COLUMN id TYPE BIGINT USING id::bigint;
```

------------------------------------------------------------------------

### 🚨 Issue 2: Not-Null 제약 조건 위반

**현상**

    null value in column "id" violates not-null constraint

**원인**\
Java에서 ID를 `null`로 저장 →\
DB에 **IDENTITY(자동 증가)** 설정이 없어 ID를 생성하지 못함

**해결**

``` sql
ALTER TABLE job_postings 
ADD GENERATED BY DEFAULT AS IDENTITY;
```

------------------------------------------------------------------------

### 🚨 Issue 3: 중복 키 및 시퀀스 불일치 (Duplicate Key)

**현상**

    duplicate key value violates unique constraint
    Key (id)=(1) already exists

**원인**\
- 기존 데이터는 ID = 1,2,3... - 새로 생성된 IDENTITY 시퀀스는 다시 1부터
시작

**해결**

``` sql
SELECT setval(
    pg_get_serial_sequence('job_postings', 'id'),
    (SELECT MAX(id) FROM job_postings)
);
```

------------------------------------------------------------------------

### 🚨 Issue 4: 저장 후 즉시 조회 시 EntityNotFound

**현상**\
공고 저장 직후 기술 스택 저장 로직에서 `INTERNAL_SERVER_ERROR` 발생

**원인**\
- `save()` 후 반환된 엔티티를 사용하지 않고 - **ID가 비어있는 기존 DTO의
ID**로 `findById()` 호출

**해결**\
`save()`가 반환하는 **영속화된 엔티티**를 후속 로직에 사용

``` java
JobPostingEntity savedJob = jobPostingRepository.save(entity);
```

------------------------------------------------------------------------

## 3. 오늘의 핵심 설정 정리

### Flyway 마이그레이션

**`V4__change_id_to_long.sql`**

``` sql
-- job_postings 테이블
ALTER TABLE job_postings ALTER COLUMN id TYPE BIGINT USING id::bigint;
ALTER TABLE job_postings DROP IDENTITY IF EXISTS;
ALTER TABLE job_postings ADD GENERATED BY DEFAULT AS IDENTITY;

-- posting_stacks 테이블
ALTER TABLE posting_stacks ALTER COLUMN id TYPE BIGINT USING id::bigint;
ALTER TABLE posting_stacks DROP IDENTITY IF EXISTS;
ALTER TABLE posting_stacks ADD GENERATED BY DEFAULT AS IDENTITY;
ALTER TABLE posting_stacks 
ALTER COLUMN job_posting_id TYPE BIGINT USING job_posting_id::bigint;
```

------------------------------------------------------------------------

### 서비스 로직 수정

**`JobPostingServiceImpl.java`**

``` java
@Transactional
public void saveJobPostingWithStacks(JobPostingDto dto) {
    // 1. 신규 등록 보장
    dto.setId(null);

    // 2. 저장된 엔티티 반환 (ID 포함)
    JobPostingEntity savedJob = saveJobPosting(dto);

    // 3. 저장된 엔티티를 기준으로 연관 관계 저장
    if (dto.getStackIds() != null) {
        for (Long sId : dto.getStackIds()) {
            TechStackEntity techStack =
                techStackRepository.findById(sId).orElseThrow(...);

            PostingStackEntity psEntity = PostingStackEntity.builder()
                    .jobPosting(savedJob)
                    .techStack(techStack)
                    .build();

            postingStackRepository.save(psEntity);
        }
    }
}
```

## 4. 배운 점

### ✅ JPA 영속성 컨텍스트와 IDENTITY 전략

-   `IDENTITY` 전략은 **DB insert 시점에 ID 생성**
-   `save()` 시 쓰기 지연 없이 즉시 쿼리 실행 가능
-   반환된 엔티티는 **ID가 채워진 영속 상태**

### ✅ 데이터베이스 마이그레이션 주의사항

-   타입 변경 시 `USING` 절로 **명시적 캐스팅**
-   Flyway SQL 수정 시 **Checksum 관리 필수**
-   `DROP ... IF EXISTS`로 멱등성 확보

### ✅ 테스트 데이터 관리

-   실패한 트랜잭션의 **찌꺼기 데이터**가 문제를 유발할 수 있음
-   로직이 정상인데 결과가 이상하면 **TRUNCATE 후 재검증**
-   때로는 DB 청소가 최고의 디버깅
