# 📝 [TIL] 2026-02-04
## Spring Boot CRUD 고도화: JPA 객체 그래프 탐색 및 DTO 최적화

단순한 DB 입출력을 넘어, 엔티티 간의 복잡한 연관 관계를 JPA로 효율적으로 조회하고 프론트엔드 요구사항에 맞춰 응답 데이터를 최적화하는 실무적인 해결 능력을 길렀다.

---

## 1. 구현 내용: 인터뷰 스케줄링 시스템 API 고도화
### 연관 관계 기반 조회 (Object Graph Navigation)
- **간접 참조 조회**: `InterviewSchedule` 엔티티와 직접 연결되지 않은 `Company` 정보를 `JobPosting`을 거쳐 조회하는 `findByJobPosting_Company_Cid` 쿼리 메서드를 구현함.
- **다대일(N:1) 관계 최적화**: 유저-공고-회사로 이어지는 계층 구조에서 `Join` 쿼리가 어떻게 발생하는지 Hibernate 로그를 통해 검증함.

### 프론트엔드 맞춤형 응답 (DTO Projection)
- **응답 필드 최적화**: 불필요한 회사 상세 정보(주소, 매출 등)를 제거해 달라는 프론트엔드 피드백을 반영하여, DTO 조립 시 필요한 필드만 선택적으로 빌드하는 `manualConvertToDto` 로직을 구현함.
- **순환 참조 방지**: 엔티티를 직접 반환하지 않고 DTO로 변환하여 JSON 직렬화 시 발생할 수 있는 무한 루프 및 `StackOverflowError`를 원천 차단함.

---

## 2. 주요 트러블슈팅

### 🚨 Issue 1. 존재하지 않는 ID 참조 시 500 에러 발생
- **현상**: 테스트 중 삭제된 ID나 잘못된 ID로 요청을 보낼 때 서버 내부 에러 발생.
- **원인**: `Optional` 처리가 미흡하여 데이터가 없을 때 `null`을 참조하려 함.
- **해결**: 
  - `orElseThrow()`를 사용하여 "데이터가 존재하지 않는다"는 명확한 예외 메시지를 던지도록 가드 로직 작성.
  - 에러 로그를 통해 로직의 정상 작동 유무를 판단하는 습관을 가짐.

### 🚨 Issue 2. 데이터 수정(Update) 시 반영 미흡
- **현상**: 서비스 로직에서 값을 바꿨음에도 DB에 반영되지 않는 현상.
- **원인**: 엔티티에 `Setter`가 없어 수동으로 값을 할당하지 못하거나, 트랜잭션 범위 밖에서 수정이 일어남.
- **해결**: 
  - 엔티티 내부에 비즈니스 메서드(`updateSchedule`)를 정의하여 캡슐화 유지.
  - `@Transactional`을 통해 JPA의 **더티 체킹(Dirty Checking)** 기능을 활용, 변경 사항이 커밋 시점에 자동으로 반영되도록 처리함.

## 3. 핵심 개념 정리

### JPA 쿼리 메서드와 언더바(`_`)
JPA에서 메서드 이름으로 쿼리를 생성할 때, `JobPosting_Company_Cid`처럼 언더바를 사용하면 엔티티 내부의 깊은 계층까지 명확하게 탐색할 수 있다. 이는 예약어나 필드명 모호성을 해결하는 중요한 규칙이다.

### DTO 조립 전략 (Manual Mapping)
`ModelMapper`나 `StructMap` 같은 라이브러리에 의존하기보다, 복잡한 연관 관계에서는 서비스 레이어에서 직접 빌더를 통해 DTO를 조립하는 것이 유지보수와 필드 제어(프론트 피드백 반영) 면에서 더 유리할 수 있다.

### 방어적 프로그래밍 (Defensive Programming)
`if (user == null)`과 같은 널 체크와 `existsBy...`를 통한 중복 데이터 검증은 서버의 안정성을 높이는 핵심 요소다. 특히 다대다 관계를 일대다-다대일로 푼 중간 테이블에서는 유니크한 조합(User + Job)을 항상 체크해야 한다.
