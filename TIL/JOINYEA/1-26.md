# 📝 [TIL] 2026-01-27: 스크랩(Scrap) 기능 설계 및 공통 응답 적용

오늘은 사용자 공고 스크랩 기능을 구현하며, 복합키 대신 대리 키를 사용한 DB 설계와 공통 응답 규격(`BaseApiResponse`)을 적용하여 API 일관성을 확보했다.

## 1. 구현 기능: 스크랩 토글 및 상태 확인
- **구조:** `User` ↔ `Scrap` ↔ `JobPosting`
- **핵심 로직:**
  - `toggleScrap`: 한 번 누르면 저장, 다시 누르면 삭제되는 토글 방식 구현.
  - `isScraped`: 공고 상세 페이지에서 현재 사용자의 스크랩 여부를 확인.
  - `getMyScraps`: 최신순(`createdAt` 내림차순)으로 사용자의 스크랩 목록 반환.

## 2. 주요 트러블슈팅

### 🚨 Issue 1: 복합키 구현의 복잡성
- **현상:** `uid`와 `pid`를 묶어 복합키로 설정하려 했으나, JPA `IdClass` 생성 등 관리 포인트가 늘어남.
- **원인:** JPA 표준 방식의 번거로움과 확장성 저하.
- **해결:** 단일 PK(`id`)를 추가하고, `uid`와 `pid`에 `Unique Constraint`를 걸어 중복 저장을 방지함.

### 🚨 Issue 2: API 응답 규격 불일치
- **현상:** 기존 `ScrapController`가 다른 도메인 API와 응답 형식이 달라 프론트엔드 연동 시 혼란 발생 가능성.
- **해결:** 프로젝트 공통 클래스인 `BaseApiResponse`를 적용하여 `code`, `message`, `data` 구조로 응답을 통일함.

## 3. 오늘의 핵심 코드 정리

### 서비스 계층 (ScrapServiceImpl)
```java
@Override
@Transactional
public boolean toggleScrap(Long uid, String pid) {
    return scrapRepository.findByUidAndPid(uid, pid)
            .map(scrap -> {
                scrapRepository.delete(scrap);
                return false; // 삭제됨
            })
            .orElseGet(() -> {
                scrapRepository.save(ScrapEntity.builder()
                        .uid(uid)
                        .pid(pid)
                        .build());
                return true; // 등록됨
            });
}
```
### 컨트롤러 계층 (ScrapController)
```java
@Operation(summary = "스크랩 토글", description = "공고를 스크랩하거나 취소합니다.")
@PostMapping
public BaseApiResponse<Boolean> toggleScrap(
        @RequestParam("uid") Long uid, @RequestParam("pid") String pid) {
    log.info("스크랩 토글 요청 - UID: {}, PID: {}", uid, pid);
    boolean result = scrapService.toggleScrap(uid, pid);
    return BaseApiResponse.ok(result);
}
