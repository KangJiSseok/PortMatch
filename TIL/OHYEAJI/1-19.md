## 2026-01-16 TIL — Git 충돌 해결, 페이지 재사용, 더미 데이터 공용화

오늘은 Git 충돌을 안전하게 해결하는 방법과, 프론트엔드에서 페이지 재사용 방식, 그리고 더미 데이터를 공용으로 관리해야 하는 이유를 정리했다. 특히 “지금 화면 일관성”과 “나중에 API 붙일 때 수정 범위 최소화” 관점이 핵심이었다.

---

### 1) Git 충돌 해결: 변경사항 유지 + dev 최신만 받아오기(stash 방식)

작업 중인 변경사항을 유지한 채로 `dev` 최신을 받아오고 싶을 때는 `stash`를 이용하는 방식이 안전하다. 로컬 변경사항을 잠깐 “서랍에 넣고” dev를 당겨온 뒤 다시 꺼내는 흐름이다.

```bash
git stash push -u -m"wip"
git pull origin dev
git stash pop
```

- `u` 옵션은 새로 만든 파일(untracked)까지 포함해 stash 한다는 의미이다.
- `git stash pop` 과정에서 충돌이 발생할 수 있으며, 충돌이 나면 해당 시점에만 충돌을 해결하면 된다.
- 이번 작업에서도 `pop` 이후 충돌이 발생하여 충돌 해결 과정을 진행했다.

---

### 2) 페이지 재사용: 같은 페이지를 role props로 분기하기

같은 화면 구조를 역할(개인/기업)에 따라 재사용하고 싶을 때는 라우팅에서 `props`로 `role`을 넘겨서 내부 로직을 분기할 수 있다.

```jsx
<Route path="/interviews" element={<InterviewListPagerole="PERSONAL" />} />
<Routepath="/company/interviews"element={<InterviewListPagerole="COMPANY" />} />
```

이 방식은 컴포넌트 중복을 줄이고, 역할에 따라 필요한 UI/데이터만 다르게 처리할 수 있어 유지보수에 유리하다.

---

### 3) 더미 데이터 공용화: 페이지마다 더미가 있으면 생기는 문제

페이지별로 더미 데이터가 따로 존재하면, 화면 간 데이터가 쉽게 어긋난다.

- MyPage는 A 데이터, InterviewList는 B 데이터처럼 서로 기준이 달라져 UX가 깨진다.
- 나중에 API를 붙일 때 페이지마다 더미 제거 + axios 호출을 각각 작성해야 해 수정 범위가 커진다.
- 정렬/필터/가공 로직이 페이지마다 중복되면서 버그 수정도 여러 곳에서 반복된다.

### 4) 공용 mock/service로 빼두면 좋은 점

더미 데이터를 공용 파일(혹은 더 나은 구조로 service 함수)로 관리하면 다음 장점이 있다.

### (1) API로 전환할 때 “한 군데만” 바꾸면 된다

지금은 더미 배열을 가공하는 함수 형태로 두고, 나중에는 그 함수 내부만 axios로 바꾸면 된다.

- `getUpcomingSessions()` : 더미 배열에서 slice
- `getSessionsByStatus()` : 더미 배열에서 filter
    
    → 추후에는 내부를 `axios.get(...)`로 변경하면 MyPage/InterviewList/Lobby가 동시에 API 데이터로 전환된다.
    

이런 이유로 `api/interview/mock.ts` 같은 공용 파일을 생성했다.

### (2) 폴더를 기능 단위로 정리하는 이유

더미/서비스 파일을 `interview` 하위로 두는 이유는 보통 API를 기능별로 관리하기 위함이며, 향후 다른 기능과 섞이는 것을 방지할 수 있다.

---

### 5) “페이지끼리 데이터를 넘긴다”에 대한 정리: id만 넘기고 다시 조회하기

페이지 간 데이터 전달은 보통 “데이터 통째로 넘기기”보다 “id만 넘기고 목적지에서 다시 조회”하는 방식이 안정적이다.

### A) URL로 id만 넘기기(권장)

- MyPage는 `interviewId` 같은 식별자만 들고 있다가
- `/interviews/101/lobby` 처럼 이동하고
- Lobby 페이지가 공용 service(API/mock)로 101번 데이터를 다시 조회해 화면을 그린다.

이 방식은 새로고침/공유/북마크에 강하고, 데이터 일관성 유지에도 유리하다.

### B) navigate state로 데이터 통째로 넘기기(비추천)

- `navigate('/...', { state: session })` 형태로 넘길 수는 있지만
- 새로고침 시 state가 사라지고 공유/북마크에도 취약하여 안정성이 떨어진다.

결론적으로 공용 mock/service를 두고, 페이지 이동은 id 기반으로 구성하는 것이 가장 자연스럽고 유지보수에 적합하다.

- (나중) API 전환 시 수정 범위를 최소화하기 위해
