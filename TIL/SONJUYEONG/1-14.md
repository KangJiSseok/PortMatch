## 🔷 2. 요구사항 명세서 작성 – 경험 및 배운 점

이번 프로젝트에서 **팀 단위 요구사항 명세서를 직접 작성**해 보았다.  
이전에는 이미 작성된 문서를 읽는 수준이었다면, 이번에는  
- 기능 정의
- 범위 확정
- 문장 정리
- 의견 통일  
까지 직접 해보며 어려움과 필요성을 체감했다.

### ✔ 느낀 점

#### 🧩 1) 요구사항 명세는 개발의 설계도이다
- 단순 기능 나열이 아니라 시스템 구조를 구축하는 과정
- “이 기능을 만들면 무엇을 입력받고, 어떤 처리를 하고, 어떤 결과를 반환하는가”를 반드시 생각해야 했다
- 명세를 작성하면서 기능 자체를 더 깊이 이해하게 되었음

#### 🔄 2) 같은 문장을 읽어도 모두의 해석은 다르다
- 로그인 기능만 해도
  - 이메일 기반?
  - OAuth 포함?
  - 비밀번호 찾기 여부?
  등의 해석 차이 존재
- 그래서 내용을 명확하게 작성하는 것이 필수

> 요구사항 명세의 목적은 **누가 읽어도 해석이 동일한 문장을 만드는 것**

#### 🧱 3) 기능을 세분화할수록 명확해진다
- 처음에는 한 줄이었던 기능이  
  → 입력 조건  
  → 출력 조건  
  → 필수 데이터  
  → 예외 처리  
까지 확장되며 더 정확해졌다

## ✍ 요구사항 명세서 작성 원칙 (이번 경험 기반)

### 1) 페이지/행위 단위로 분할
- ex. 회원가입 / 기업 등록 / 이력서 업로드 / AI 분석

### 2) 사용자 관점 표현
- “누가 어떤 동작을 할 수 있는가” 중심 문장

### 3) 입력 / 출력 / 필수 조건 정의
- 필수값 & 선택값 구분
- 어떤 데이터가 DB로 저장되는지도 명확히

### 4) 예외 및 분기 처리 명시
- 기업 없는 경우 자동 등록
- 분석 실패 시 대응 방법
- 로그인 실패 처리

### 5) 유형 태깅 시스템 사용
- 기능 유형: C/R/U/D/S/L
- 기술 속성: UI / BI / DA / IF

> 요구사항 명세서는 개발 직전에 팀이 읽는 마지막 진리 문서다

## 🧩 3. Git Convention & Flow

### 📌 브랜치 구조
- **master** : 최종 배포
- **develop/app**, **develop/back** : 각 도메인 개발 메인
- **feat/** : 기능 개발 브랜치  
  예: `feat/app/add-login`
- **hotfix/** : 긴급 수정

> 모든 기능은 develop에서 출발 → develop로 돌아온다

### 📌 Git 사용 규칙
1. master 직접 push 금지
2. commit/push 전 반드시 pull
3. 다른 사람 코드 임의 수정 금지
4. 자주 나누어 commit & push

### 📌 Commit 메시지 규칙


| 타입 | 의미 |
|------|------|
| feat | 기능 추가 |
| fix | 버그 수정 |
| docs | 문서 수정 |
| style | 포맷 수정 |
| refactor | 구조 변경 |
| test | 테스트 |
| chore | 설정 변경 |
| hotfix | 긴급 문제 |
| init | 초기 세팅 |

## 💻 4. Code Convention

### ✔ Backend – Naver Java Style 요약
- 들여쓰기 4 space
- 클래스/메서드/변수는 의미 중심 네이밍
- CONSTANT 는 `UPPER_SNAKE_CASE`
- 함수는 단일 책임 원칙 적용
- import 정리, dead code 제거 필수
- 공백과 줄 바꿈으로 가독성 확보

> 규칙은 개성 제거가 아니라 협업 안정화를 위한 최소 공통점

## 🌀 6. Jira와 연동한 개발 흐름

### Jira 개념 정리
- **Epic**: 큰 단위 기능 묶음
- **Story/Task**: 개발 가능한 단위
- **Backlog**: 앞으로 처리할 작업의 대기열
- **Sprint**: 1~2주 단위로 실행하는 개발 주기
- **Story Point**: 난이도 & 작업량 추정 값

### Jira 개발 프로세스
1. 요구사항 → 작업(Task) 생성
2. SP 추정, 난이도 평가
3. 백로그에서 스프린트로 작업 할당
4. 진행 상태 업데이트  
   `To Do → In Progress → Review → Done`
5. 데일리 회의 + 번다운 확인
6. 완료 후 스프린트 회고 진행

## 📉 7. 번다운 차트 – 깨달은 점

### 번다운 차트란?
스프린트 기간 동안 남은 작업량이  
얼마나 꾸준히 감소하고 있는지 시각화한 차트

### 배운 점 및 인사이트
- 그래프가 내려가지 않는다는 것은
  - 태스크 크기가 과도하거나
  - 이슈가 발생했거나
  - 작업이 막혀있다는 빨간 신호
- 마지막에 몰아 처리하면
  - 일정 미준수
  - 낮은 품질
  - 번아웃 위험

> 번다운 차트는 단순 결과물이 아니라  
> **팀의 현재 상태를 보여주는 체온계**이다

## 🎯 오늘의 핵심 요약

- 요구사항 명세 작성은 “아이디어 → 시스템”의 첫 번째 현실화 과정
- 명확하지 않은 문장은 곧 개발 리스크로 전가된다
- Git Flow + Commit Convention은 협업의 공용 언어 역할
- Jira는 진행 현황을 눈에 보이게 만들고,
- 번다운 차트는 속도와 리스크를 실시간으로 드러낸다
- 결국 프로젝트 성공의 기반은  
  **명확한 문서 + 일관된 코드 + 규칙 있는 소통**
