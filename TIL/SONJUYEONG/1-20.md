## 1️⃣ Spring Security는 무엇을 해결해주는가

Spring Security는 단순히 “로그인 라이브러리”가 아니다.
웹 애플리케이션에서 다음 두 가지를 표준적이고 안전하게 처리하기 위한 프레임워크다.

1. **인증(Authentication)**
   → 사용자가 누구인지 확인
2. **인가(Authorization)**
   → 해당 사용자가 어떤 요청을 할 수 있는지 결정

Spring MVC만 사용할 경우

* 로그인 상태 관리
* 비밀번호 암호화
* 요청별 접근 제어
  를 모두 직접 구현해야 하지만,

Spring Security는 이를 **필터 체인 구조**로 제공한다.

---

## 2️⃣ Spring Security의 핵심 구조

### 🔹 Security Filter Chain

Spring Security의 모든 동작은 **서블릿 필터**에서 시작한다.

```text
요청
 → Security Filter Chain
   → 인증 관련 필터
   → 인가 관련 필터
 → Controller
```

* Controller에 도달하기 전에
* 요청은 반드시 Security 필터들을 통과한다
* `permitAll()`이어도 **필터를 아예 안 타는 것은 아님**

👉 이 점을 이해하지 못하면
`403 Forbidden`이 왜 나는지 감이 안 온다.

---

## 3️⃣ SecurityConfig (SpringConfigure 코드)의 역할

보통 다음과 같은 설정 클래스를 만든다.

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {
}
```

이 클래스의 역할은:

* 어떤 요청을 허용할지
* 어떤 요청을 막을지
* 로그인 / 로그아웃 방식을 어떻게 할지
* 세션을 사용할지 말지
* 비밀번호 암호화 방식을 무엇으로 할지

👉 **Spring Security의 행동 규칙을 정의하는 설계도**

---

### 🔹 authorizeHttpRequests()

```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/api/auth/login").permitAll()
    .anyRequest().authenticated()
)
```

의미 해석:

* `/api/auth/login`
  → 로그인하지 않아도 접근 가능
* 그 외 모든 요청
  → 인증된 사용자만 접근 가능

중요한 점:

* `permitAll()` = 접근 허용
* **Security를 끈 것이 아님**

## 4️⃣ Authentication / Authorization 개념 분리

### 🔹 Authentication (인증)

* “이 사람이 누구인가?”
* 아이디 + 비밀번호 검증
* 성공 시:

  * Authentication 객체 생성
  * SecurityContext에 저장

### 🔹 Authorization (인가)

* “이 사람이 이 요청을 해도 되는가?”
* 인증 이후에 검사
* 권한(Role) 기준으로 판단

👉 **403 Forbidden은 인가 실패**
👉 **401 Unauthorized는 인증 실패**

---

## 5️⃣ PasswordEncoder란?

Spring Security에서 **비밀번호는 절대 평문 저장 금지**다.

그래서 등장하는 것이 `PasswordEncoder`.

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

### 🔹 역할

* 회원가입 시:

  * 비밀번호를 **암호화해서 DB에 저장**
* 로그인 시:

  * 입력한 비밀번호를 암호화
  * DB에 저장된 암호화 값과 비교

👉 즉,

> 같은 비밀번호라도
> 매번 다른 암호화 결과가 나온다 (salt)

---

### 🔹 왜 BCrypt인가?

* 단방향 암호화
* 무차별 대입 공격에 강함
* Spring Security 기본 권장 방식

---

## 6️⃣ UserDetails / UserDetailsService

Spring Security는
“User 엔티티”를 **직접 쓰지 않는다**.

대신 다음 구조를 사용한다.

### 🔹 UserDetails

* Spring Security가 이해할 수 있는 사용자 정보 인터페이스
* 포함 정보:

  * username
  * password
  * 권한 목록
  * 계정 만료 여부 등

👉 보통

* 기존 User 엔티티를 감싸는 Adapter 형태로 구현

---

### 🔹 UserDetailsService

```java
public interface UserDetailsService {
    UserDetails loadUserByUsername(String username);
}
```

역할:

* 로그인 시
* username(email 등)을 받아서
* 사용자 정보를 조회해 반환

👉 로그인 검증의 핵심 진입 지점

---

## 7️⃣ Authentication 객체와 Principal

### 🔹 Principal이란?

* 현재 인증된 사용자 정보
* Spring Security에서 로그인 성공 시 생성됨

```java
Authentication authentication;
authentication.getPrincipal();
```

보통 Principal에는:

* UserDetails 구현체
* 또는 사용자 식별 정보

---

### 🔹 Controller에서 사용하는 방법

```java
@GetMapping("/me")
public UserResponse me(Authentication authentication) {
    return ...
}
```

의미:

* SecurityContext에 저장된 인증 정보 주입
* 별도로 세션에서 꺼낼 필요 없음

👉 **“현재 로그인한 사용자”를 가져오는 표준 방식**

---

## 8️⃣ SecurityContext와 세션

### 🔹 인증 정보는 어디에 저장될까?

* 로그인 성공 시
* Authentication 객체가
* SecurityContext에 저장됨

기본 설정:

* SecurityContext는 **HTTP Session**에 저장
* 클라이언트는 `JSESSIONID` 쿠키만 가짐

👉 그래서:

* Headers에는 인증 정보가 없고
* Cookies에만 존재하는 것이 정상

---

## 9️⃣ logout의 실제 의미

로그아웃이란:

* 세션 무효화
* SecurityContext 제거

```java
.logout(logout -> logout
    .logoutUrl("/api/auth/logout")
)
```

중요:

* 로그아웃 이후
* 보호된 API 호출 → 403 발생

👉 로그아웃이 실패한 게 아니라
👉 **그 다음 요청이 인가 실패한 것**

---

## 🔟 Spring Security를 처음 써보며 느낀 점

* Security는 “마법”이 아니다
* 모든 동작은 **필터 + 객체 흐름**
* 에러 메시지보다 **흐름 이해가 중요**

특히:

* permitAll ≠ Security 무시
* 403 ≠ 로그인 안 됨
* 인증 정보는 서버가 관리
