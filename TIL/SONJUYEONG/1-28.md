# TIL – 임베딩 설계 및 유사도 측정 방식 개선 과정

## 📌 배경

포트폴리오 프로젝트와 기업 프로젝트 간의 **도메인 유사도 기반 매칭 기능**을 구현하면서, 단순 코사인 유사도 비교만으로는 정확도가 충분하지 않다는 문제를 느꼈다.

특히 다음과 같은 문제가 있었다.

* 일부 필드가 비어 있는 데이터도 동일한 가중치로 비교됨
* 임베딩 텍스트 구조가 일관되지 않아 비교 기준이 모호함
* 기업 프로젝트의 도메인 정의가 포트폴리오 도메인과 맞지 않음
* 유사도 점수가 직관적으로 신뢰되지 않는 경우가 발생

이를 해결하기 위해 다음 4가지 방향으로 개선을 진행했다.

---

## 1️⃣ 유사도 측정 시 비어 있는 필드 패널티 부여

### 🔍 기존 방식

기존 유사도 계산 방식은 필드별 가중치를 적용하여 다음과 같이 처리했다.

* project_name
* problem
* solution
* tech
  각 필드를 임베딩 후 코사인 유사도를 계산하고 가중합으로 최종 점수를 산출

그러나 문제는:

* 특정 필드가 비어 있어도 다른 필드 점수만으로 높은 유사도가 나오는 경우 발생
* 정보가 부족한 데이터가 오히려 유리해지는 왜곡 현상 발생

### ✅ 개선 방향

필드가 비어 있는 경우 **패널티를 적용**하는 로직을 추가했다.

개념적으로는 다음과 같다.

* 비교 대상 필드가 비어 있으면:

  * 해당 필드 점수를 0으로 처리
  * 또는 전체 점수에서 패널티 비율 차감
* 정보가 많은 프로젝트가 더 정당한 평가를 받도록 유도

이를 통해:

* 데이터 품질이 유사도 결과에 반영됨
* 불완전한 데이터가 상위 매칭되는 현상을 줄일 수 있었음

---

## 2️⃣ 임베딩 모델 변경

### 🔍 문제 인식

기존 임베딩 모델은 영어 중심이거나 일반 문장 임베딩에 최적화되어 있어,
한국어 기반 포트폴리오/기업 프로젝트 텍스트에 대해 미묘한 한계를 느꼈다.

또한:

* 도메인 필드 추가
* 텍스트 구조 변경
  등 설계 변경이 있었기 때문에, 임베딩 모델도 함께 재검토할 필요가 있었다.

### ✅ 개선 방향

임베딩 모델을 다음 기준으로 수정하였다.

* 한국어 문맥 이해 성능
* 프로젝트 설명 텍스트에 대한 표현력
* 장기적으로 안정적으로 사용 가능한 모델

---

## 3️⃣ 임베딩 설계에 `domain` 필드 추가

### 🔍 기존 임베딩 구조 예시

기존에는 주로 다음 정보만 임베딩했다.

```
[프로젝트명]
[문제]
[해결방법]
[기술스택]
```

하지만 기업 프로젝트와 포트폴리오 프로젝트를 비교할 때:

* 기술은 비슷하지만 도메인이 다른 경우

  * 예: 의료 서비스 vs 채용 서비스
* 도메인 차이가 반영되지 않는 문제가 발생

### ✅ 개선 방향

임베딩 텍스트에 `domain` 필드를 추가하였다.

예시:

```
[도메인] 헬스케어
[프로젝트명] 시선 추적 기반 환자 커뮤니케이션 플랫폼
[문제] ALS 환자의 의사소통 어려움
[해결] 시선 추적과 딥러닝 기반 입력 시스템 구현
[기술] OpenCV, Spring, Flask
```

이를 통해:

* 임베딩 벡터에 산업/서비스 맥락이 함께 반영
* 기술 중심 유사도에서 도메인 중심 유사도로 확장 가능

---

## 4️⃣ `domain` 필드에 어떤 내용을 넣을 것인가에 대한 고민

### 🔍 문제

domain 필드에 들어갈 값의 깊이에 따라 유사도 측정 값이 달라질 수 있다.

예:

* "AI 헬스케어 플랫폼"
* "의료 영상 분석 시스템"
* "시선 추적 기반 커뮤니케이션 서비스"
* "환자 보조 시스템"
vs
* "의료"
* "교육"
* "금융"


* 특히 포트폴리오 domain과 기업 프로젝트의 domain 형태가 다를 경우
* 임베딩 결과가 불안정해짐
* 같은 산업인데 서로 다른 벡터로 분산됨

### ✅ 해결 방안

domain 필드는 **여러 케이스로 나누어** 테스트를 통해 확정짓기로 결정했다.

* 도메인 대분류
* 도메인 구체화
* 도메인 대분류 밑에 하위 분류 추가

domain 케이스를 위의 3가지의 경우로 나누어 실험할 예정

## ✨ 느낀 점

이번 작업을 통해 중요한 것은:

* **어떤 임베딩 모델을 사용할 것인가**
* **임베딩에 어떤 정보를 넣을 것인가**
* **유사도를 어떻게 해석할 것인가**
* **데이터 구조를 어떻게 설계할 것인가**

라는 점이라는 것을 느꼈다.

특히:

* 비어 있는 필드에 대한 패널티
* domain 필드의 의미 정의
* 임베딩 텍스트 구조 통일

은 모델 성능보다 더 중요한 설계 요소였다.

임베딩 기반 시스템은 결국:

> 모델 + 데이터 설계 + 유사도 정책
> 의 조합이라는 점을 체감한 하루였다.
