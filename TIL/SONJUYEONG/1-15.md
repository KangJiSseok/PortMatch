# 🏗️ TIL — 시스템 아키텍처의 구성 요소와 흐름 이해

오늘은 **시스템 아키텍처가 어떤 단계와 논리를 통해 만들어지는지** 배웠다.  
단순히 서버, DB, 프론트엔드가 연결된 그림을 그리는 것이 아니라  
**누가 사용하는지 → 무엇을 해야 하는지 → 어떤 기준을 만족해야 하는지**  
→ **그래서 시스템이 어떻게 구성되어야 하는지**  
라는 논리적 흐름 위에서 아키텍처가 정의된다는 것을 깨달았다.

---

## 1️⃣ 이해관계자 (Stakeholders) 선별

시스템 설계의 첫 단계는 **이 시스템에 의해 영향을 받는 모든 주체를 식별하는 것**이다.  
이해관계자는 **사람일 수도, 조직일 수도, 외부 시스템일 수도 있다.**

> 아키텍처는 결국 “누구를 위해 만드는가”를 명확히 하는 것에서 시작된다.

### 📝 예시
- 학생
- 교수
- 교직원
- 인사관리 시스템 (외부 연동)
- 학사관리 시스템 (내부 시스템)

✔ 시스템에 접속하는 사용자뿐 아니라  
✔ 데이터를 주고받거나 연동되는 시스템까지 포함된다는 점이 인상적이었다.

---

## 2️⃣ 기능 요구사항 정의 (Functional Requirements)

이해관계자가 무엇을 하고 싶은지를 **기능(Feature)** 단위로 적는다.  
즉, 시스템이 반드시 제공해야 하는 서비스이다.

> **"사용자가 이 시스템을 통해 무엇을 할 수 있어야 하는가?"**

### 📝 예시
- 학사 관리
- 수업 관리
- 수강 신청
- 사용자 권한 관리

✔ 요구사항 명세서에서 봤던 **CRUD + UI/BI/DA/IF** 분류 체계가  
기능을 더욱 정교하게 정의하는 데 도움이 된다고 느꼈다.

---

## 3️⃣ 비기능 요구사항 정의 (Non-Functional Requirements)

기능을 “어떻게” 제공해야 하는지에 대한 기준과 제약을 정하는 단계.  
성능, 보안, 확장성, 장애 대응, 사용성 등 시스템 품질을 결정한다.

> **기능은 있어도 비기능 요구사항이 형편없으면 서비스가 망한다.**

### 📝 예시
- 동시 접속에도 문제없이 수강 신청 처리
- 어디서든 접근 가능한 안정적인 서비스 환경
- 웹/모바일 플랫폼 지원
- 사용자 권한에 따른 접근 통제
- 장애 발생 시 데이터 손실 최소화

✔ 배포 후 드러나는 문제 대부분이 **비기능 요구사항 미정의**에서 발생한다는 사실을 배웠다.

---

## 4️⃣ 품질 속성 시나리오(Quality Attribute Scenario)

비기능 요구사항을 **측정 가능하게 표현하는 공식적인 문장 구조**.  
실제 상황을 가정해 시스템이 어떤 반응을 해야 하는지 구체화한다.

### 📌 시나리오 구성 요소
| 요소 | 의미 |
|---|---|
| Source | 누가/어디서 자극(stimulus)을 발생시키는가 |
| Stimulus | 발생하는 이벤트(요구, 장애, 입력 등) |
| Environment | 언제/어떤 상황에 발생하는가 |
| Artifact | 영향을 받는 시스템 요소 |
| Response | 시스템의 기대 동작 |
| Response Measure | 측정 가능한 만족 조건 (성능 기준 등) |

### 🧩 예시(실제 학사 시스템 예제 기반)

#### 📌 성능 - 수강신청 폭주 처리
- **Source:** 학생 다수  
- **Stimulus:** 동시에 수강신청 요청  
- **Environment:** 학기 시작 전날, 피크 시간  
- **Artifact:** 수강신청 시스템  
- **Response:** 요청을 순서대로 처리  
- **Response Measure:** 각 요청을 2초 이내 처리

#### 📌 보안 - 권한 관리
- **Source:** 학생/비인가 사용자  
- **Stimulus:** 로그인 시도 및 비정상 접근 발생  
- **Environment:** 외부 네트워크 포함  
- **Artifact:** 인증/권한 시스템  
- **Response:** 접근 차단, 알림 로그 생성  
- **Response Measure:** 차단까지 1초 이내

#### 📌 가용성 - 장애 복구
- **Source:** 내부 서비스 모듈  
- **Stimulus:** 서비스 인스턴스 장애 발생  
- **Environment:** 고가용성 환경  
- **Artifact:** 서비스 디스커버리/로드밸런서  
- **Response:** 문제 인스턴스를 트래픽 대상에서 제외  
- **Response Measure:** Failover를 5초 이내 처리

✔ “비기능 요구사항 → 시나리오 → 측정 기준”의 연결 고리가 정말 중요하다.

## 5️⃣ 시스템 아키텍처 구성

마지막 단계는 **앞 단계에서 정의된 요구사항을 충족하는 구조를 설계하는 것**이다.

### 📌 핵심 개념
- **사용자 → App/웹 → Load Balancer → WAS → DB 구조**
- 역할별 서버 분리 (예: 학사 관리 / 인사 관리 / 수강신청)
- 고가용성 구성
  - Active-Standby Cache
  - Job Queue + Job Server
- 확장 가능한 아키텍처 설계 (Scale-out)

### 🧱 예시 구성 흐름
1. 학생/사용자가 웹/앱에서 요청을 보낸다  
2. 요청은 Load Balancer로 전달되어 적절한 WAS로 분배된다  
3. WAS는 담당 역할에 따라 서로 다른 데이터베이스와 연동된다  
4. 수강신청처럼 트래픽이 폭주하는 영역은 별도 WAS + 캐시 + 큐로 분산  
5. 장애 발생 시, 사용자는 눈치채지 못하도록 자동 페일오버 처리  
6. 전체 구성은 클라우드 상에서 컨테이너 기반으로 관리될 수 있음  
   (예: AWS, Docker, Kubernetes, Redis, PostgreSQL)

✔ 아키텍처는 그저 박스와 화살표가 아니라,  
✔ **요구사항을 충족시키기 위한 구조적 해답**이라는 걸 이해했다.

---

## 🧠 오늘의 핵심 인사이트

- 아키텍처는 **그림의 예쁨이 아니라 논리의 설득력**이다.
- 기능만 있으면 되는 줄 알았지만  
  실제로 서비스가 살아남는 핵심은 **비기능 요구사항**이었다.
- “누가, 무엇을, 어떤 기준으로, 어떤 구조에서”  
  이 순서를 따라야 설계가 비로소 **완성된 설명**이 된다.
- 요구사항 분석 → 품질속성 시나리오 → 아키텍처는  
  개발 이전에 반드시 통과해야 할 **논리적 단계**임을 깨달았다.

---

## 💬 배운 점 & 느낀 점

- 지금까지는 아키텍처를 보면 그냥 “서버 여러 개 쓰는 그림” 정도로 생각했다.
- 하지만 실제 서비스는 **폭주, 장애, 권한, 보안, 확장성**이 현실 문제이며  
  이것을 고려하지 않으면 서비스를 유지할 수 없다.
- 따라서 앞으로는 기능 구현 중심의 사고에서 벗어나  
  “이 기능이 실 서비스 환경에서 문제 없이 돌아갈까?”를 먼저 고민할 것.
