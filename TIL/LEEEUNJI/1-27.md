## 1. 검색 UX의 기준을 명확히 정의하기

검색창에서 아무 것도 입력하지 않거나  
공백만 입력한 상태로 검색을 시도했을 때의 동작을 고민했다.

단순히 “아무 동작도 하지 않음”보다는,  
**전체 공고 조회 페이지로 이동시키는 것이 더 직관적**이라고 판단했다.

이를 위해:
- 검색어에 `trim()`을 적용하고
- 값이 비어 있으면 `/job-postings`로 이동하도록 처리했다.

👉 검색 UX의 기준을 **코드로 명확히 고정**한 경험이었다.

---

## 2. 검색 기준 변경: 회사명이 아닌 ‘공고 제목(keyword)’

초기에는 회사명을 기준으로 검색하도록 구현했지만,  
Swagger API 명세를 확인해보니 실제 제공되는 검색 API는  
**“공고 제목에 keyword가 포함된 공고 검색”**이었다.

이에 따라 프론트 검색 기준을 다음과 같이 수정했다.

- ❌ 회사명(companyName) 기준 검색
- ⭕ 공고 제목(title)에 keyword 포함 여부로 검색

프론트 구현은 항상 **API 스펙을 기준으로 맞춰야 한다**는 점을 다시 한 번 체감했다.

---

## 3. URL Query Parameter를 검색 상태의 기준으로 삼기

검색어를 컴포넌트 state로만 관리하지 않고,  
`keyword`를 **URL query parameter**로 관리하도록 구조를 정리했다.

이 방식의 장점:
- 새로고침해도 검색 상태 유지
- 뒤로가기/앞으로가기 시 검색 결과 복원
- 필터, 정렬, 페이지네이션과 자연스럽게 결합 가능

👉 검색 상태의 **Single Source of Truth를 URL로 두는 구조**를 확립했다.

---


## 4. 프론트엔드 API 연동을 준비하며 정리한 기준

공고 검색 페이지를 API와 연동하기 전,  
Swagger·Network 탭·DB(DBeaver)를 기준으로 데이터를 점검했다.

그 과정에서 다음을 확인했다.

- 공고 `id` 타입은 **string**
- `endDate`는 `"YYYY-MM-DD"` 형식의 날짜 문자열
- 기술 스택 테이블은 `tech_stacks`이며, 현재 데이터는 비어 있음
- Swagger 문서와 실데이터는 **차이가 있을 수 있음**

👉 API 연동은 문서가 아니라  
**실제 응답과 DB 구조를 기준으로 판단해야 한다**는 점을 명확히 했다.

---

## 5. 백엔드 응답 타입과 프론트 UI 타입은 다르다

백엔드 API는 도메인 중심 구조이고,  
프론트엔드는 화면 표현에 최적화된 구조를 필요로 한다.

따라서 두 구조 사이에는 반드시 **변환 계층(adaptor)** 이 필요하다.

예시:
- `company.corpName` → `company`
- `company.logo` → 카드 UI의 `logo`
- `endDate` → 화면에서 사용할 `deadline`
- `id` 타입 불일치 (`string` ↔ `number`)

👉 API 응답을 그대로 UI에 쓰기보다,  
**프론트에서 한 번 가공해서 사용하는 구조가 더 안전**하다는 결론에 도달했다.

## 6. React Query 훅(useQuery)의 역할 정리

훅(hook)은 **상태와 로직을 묶어 재사용하기 위한 함수**다.  
React Query 훅은 단순한 API 호출을 넘어 다음을 담당한다.

- API 요청 트리거
- 로딩 상태 관리
- 에러 상태 관리
- 캐싱 및 중복 요청 방지

페이지 컴포넌트에서 axios를 직접 호출하지 않고,  
`useJobPostings` 같은 **커스텀 훅으로 분리하는 이유**를 명확히 이해했다.
