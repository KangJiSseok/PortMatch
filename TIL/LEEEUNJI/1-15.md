# 📘 01/15 TIL – 아키텍처 설계 & 기획 단계 이해

## 1. JPA Entity와 Django Model의 관계

- JPA의 **Entity**는 Django의 **Model**과 거의 동일한 개념이다.
- 둘 다 **DB 테이블을 코드 객체로 매핑하는 ORM 개념**이다.
- 차이점은 구조:
    - Django: `Model` 하나로 ORM 역할까지 포함
    - Spring: `Entity(데이터)` + `Repository(DB 접근)`로 역할 분리
- 결론적으로 **개념은 같고, 책임 분리 방식만 다르다**.

---

## 2. MSA(Microservice Architecture)의 핵심 개념

- MSA는 하나의 큰 서비스를 **기능 단위의 작은 서비스들로 분리**하는 아키텍처이다.
- 각 서비스는:
    - 독립 배포 가능
    - 독립 장애
    - 필요 시 다른 기술 스택 사용 가능
- 단점:
    - 구조/운영 복잡도 증가
    - 초기 프로젝트에는 과한 선택일 수 있음
- 결론:
    - **초기 프로젝트는 모놀리식 + 도메인 분리**
    - MSA 개념은 “설계 관점”으로만 이해하는 게 적절

---

## 3. 파이프라인, inner 서비스, 바운더리 개념 정리

### 파이프라인

- 요청 → 처리 → 처리 → 응답의 **흐름**
- 이 흐름을 **같은 서비스 내부 호출로 할지**,
    
    **REST API로 분리할지**를 결정하는 것이 핵심 고민
    

### inner 서비스

- 외부(프론트/API)에서 직접 호출하지 않는 **내부 전용 로직**
- 같은 도메인/서비스 내부에서만 사용
- 예: 권한 체크, 검증 로직, 내부 계산

### 바운더리(boundary)

- “여기까지가 이 서비스의 책임”이라는 **경계**
- 경계를 넘을 때는:
    - 직접 DB 접근 ❌
    - API 호출 ⭕
- 바운더리를 잘 나누면 결합도↓, 유지보수성↑

## 4. ERD vs API 명세서 – 무엇을 먼저?

### 기본 원칙

- **정해진 절대 순서는 없다**
- 하지만 실무에서는 **ERD → API**가 더 일반적

### 경우별 정리

- ✔ 파이프라인이 분리된 구조(MSA/서비스 분리):
    - **서비스 간 API 계약 먼저**
    - 각 서비스 내부 ERD는 이후에 설계
- ✔ 하나의 서비스(모놀리식/공유 DB):
    - **ERD 초안 → API 명세**
    - 이후 개발하면서 왕복 수정

### 핵심 결론

> ERD와 API는 일방향이 아니라 반복적으로 함께 다듬는다
>

## 5. 크롤러 설계에 대한 이해

- 크롤러는 **우리 서비스가 아니라 데이터 수집용 워커**
- 유저 요청을 처리하는 서버와 **역할이 완전히 다름**
- 따라서:
    - 서비스 서버와 **분리된 인스턴스/서버**에서 운영하는 것이 안전
    - 장애, 리소스 사용, 네트워크 정책을 분리 가능

### 크롤러 개수 결정 기준

- 갱신 주기 (하루 1회 / 몇 시간 단위 등)
- 수집 대상 규모 (페이지 수, 기업 수)
- 대상 사이트의 요청 제한(Rate Limit)
- 초기에는:
    - **워커 1개로 시작**
    - 큐 기반 구조로 **확장 가능하게 설계**하는 것이 최선
