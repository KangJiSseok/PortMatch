## 1. Git rebase 사용 이유와 흐름 이해

### 핵심 정의

- `rebase`는 내 커밋을 다른 브랜치 최신 커밋 위로 **다시 얹는 방식**

### 사용 방법

```bash
git pull --rebase origin docs
git config --global pull.rebase true
```

- 위 설정을 하면 이후 `git pull` 시 기본적으로 rebase 적용

### merge vs rebase 차이

- **merge**: 히스토리가 복잡해질 수 있음
- **rebase**: 히스토리가 깔끔, 협업 시 리뷰/추적이 쉬움

### 결론

- 공유 브랜치에서는 **rebase가 협업 친화적**

> **한 줄 정리**: rebase는 "과거를 정리해서 현재에 맞게 다시 놓는 방식"이다.

    을 거쳐야 함

> **핵심**: AI는 판단 주체가 아니라 보조 도구

## 3. 아키텍처 개념 정리 (MSA vs 3-Tier)

### MSA (Microservice Architecture)

- 서비스 단위 분리
- 독립 배포 / 장애 격리 가능
- 대신 운영/설계 난이도 ↑

### 3-Tier

- Presentation / Application / Data
- 구조 단순, 이해 쉬움
- 초기 프로젝트에 적합

### 결론

- 아키텍처는 **유행이 아니라 상황 선택**
- 지금 단계에서는:
    - MSA는 "설계 관점 이해"
    - 실제 구현은 **단순한 구조**가 맞음

## 4. 기획은 한 번에 완벽할 수 없다는 사실

### 깨달은 점

- 모든 요구사항을 처음부터 완벽히 정의하는 건 **불가능**
- 큰 덩어리 → 점진적 구체화가 현실적인 접근

### 올바른 흐름

1. 큰 기능 단위 정의
2. 핵심 파이프라인 정리
3. 구현하면서 세부 보완

> **핵심**: 기획은 고정 문서가 아니라 진화하는 설계

## 5. 로그인 방식의 큰 그림

### 두 가지 방식

- **세션 기반**
- **토큰 기반** (JWT 등)

### 핵심 차이

- 세션: 서버 상태 유지 (stateful)
- 토큰: 서버 무상태 (stateless)

### 결론

- 어떤 방식이 "더 좋다"가 아니라
- **아키텍처/확장성/보안 요구에 따라 선택**
