## 1️. 프론트–백엔드 타입 불일치 문제를 어떻게 해결했는가

### 문제 상황
- DB / 백엔드 / 프론트에서 `id` 타입이 서로 다름
  - DB: 숫자
  - 백엔드: `Long`
  - 프론트: `string`으로 가정하고 처리하던 코드 존재

### 해결 과정
- DBeaver로 실제 DB 테이블 확인
- `job_postings.id`에는 **숫자만 저장**되고 있음을 확인
- 프론트 타입을 `number` 기준으로 통일
- 정렬 로직에서 불필요한 조건 제거 (`sortLatest` 단순화)

> **“타입 논쟁은 코드로 하지 말고 DB를 보고 결정한다”**

---

## 2. DTO → UI Model 매핑 계층의 역할

### 왜 DTO를 그대로 쓰지 않았는가
- API 응답은 **데이터 전달 목적**
- UI는 **표현 목적** → 요구사항이 다름

### `mapDtoToUiJob`에서 처리한 것들
- 회사명 / 로고 / 위치 fallback 처리
- `endDate` → `D-n / 오늘마감 / 마감` 문자열 가공
- `jobType(number)` → UI 라벨(`신입 / 신입·경력 / 경력`) 변환
- 프론트에서 바로 쓰기 좋은 형태로 구조 변환
> **“UI는 API 스펙을 그대로 믿으면 안 된다”**

---

## 3️. PostgreSQL + JPA 스네이크 케이스 매핑 이해

### 구조
- DB 컬럼: `snake_case`
- 엔티티 필드: `camelCase`

### 왜 문제없이 동작하는가
- JPA의 네이밍 전략 덕분에 자동 매핑
- 단, 컬럼 정의가 헷갈릴 경우 직접 확인 필요

### 실제로 한 일
- DBeaver에서 PK, FK, 컬럼 타입 직접 확인
- 엔티티 설계가 DB와 일치함을 검증

> **“ORM을 믿되, 스키마는 직접 확인하자”**

---


## 4. 데이터가 없으면 기능 검증도 없다

### 혼란의 원인
- DB에 공고 데이터가 1개뿐인 상태
- 검색 / 필터 / 정렬이 안 되는 것처럼 보였음

### 깨달음
- 연동 문제 ❌  
- 데이터 부족 문제 ⭕  

### 해결
- DBeaver로 더미 데이터 직접 INSERT
- 기업별 공고, 기술 스택 매핑 데이터 확보

> **“프론트 문제처럼 보이는 것의 절반은 데이터 문제다”**
