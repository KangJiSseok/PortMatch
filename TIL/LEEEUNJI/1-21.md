##  1. 공통 Button 컴포넌트 구조 이해
- variant, size, colorTheme는 버튼의 역할·외형·맥락을 분리하기 위한 props
- 기본값을 주는 이유: 버튼 사용 시 매번 옵션을 강제하지 않기 위해서
- baseStyles는 모든 버튼이 공유하는 공통 뼈대
- sizes에서 variant === 'close'를 분기한 이유: 텍스트 버튼과 아이콘 버튼의 레이아웃 성격이 다르기 때문
- relative는 버튼 위치를 바꾸기 위한 게 아니라: badge 같은 absolute 요소의 기준점 역할

> 공통 컴포넌트는 “많이 쓰는 코드”가 아니라
> 많이 확장될 수 있도록 만든 코드라는 걸 체감했다.

## 2. Docker 실행 에러 원인 분석
- version is obsolete는 경고일 뿐, 실행 실패 원인은 아님
- 진짜 에러는
→ Docker Compose가 참조하는 .env 파일이 없었던 것
- Docker는 실행 환경을 엄격히 고정하기 때문에
→ 환경 파일 누락을 그냥 넘어가지 않는다


## 3. Docker 개념 정리 (vs venv)
- venv는 파이썬 패키지 수준의 격리
- Docker는 실행 환경 전체(OS + 런타임 + 라이브러리)의 격리
- Docker는 “고급 venv”가 아니라
→ 아예 다른 레벨의 개념

> 팀 프로젝트에서 Docker를 쓰는 이유는
> 편의성이 아니라 환경 통일과 재현성 때문이다.

## 4. Docker 이미지 빌드
- Docker 이미지화는 docker build
- docker compose up은 이미지를 “만드는 명령”이 아니라 이미지를 기반으로 “실행하는 명령”
- 이미지와 컨테이너는
→ 설계도와 실행 결과의 관계

> Docker 흐름이
> Dockerfile → Image → Container로 머릿속에 정리됐다.


## 5. CI/CD에서 Docker를 쓰는 이유
- Docker는 CI/CD에서 실행 환경을 고정하고
- 빌드·테스트·배포를 동일한 이미지로 반복하며 서버에는 실행만 시키게 만든다
>  CI/CD에서 Docker는 선택이 아니라
전제 조건에 가깝다는 느낌을 받았다.

## 6. Docker 이미지 개념 심화
- Docker 이미지:  단일 실행파일은 아니지만 실행에 필요한 모든 것을 포함한 실행 패키지
- 이미지 크기는 base image, Dockerfile 구조에 따라 크게 달라진다
- 멀티 스테이지 빌드, .dockerignore로 충분히 경량화 가능

> Docker 이미지는
“만드는 순간 품질이 결정되는 산출물”이라는 인식이 생겼다.
