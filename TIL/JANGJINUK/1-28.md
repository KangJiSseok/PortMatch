## 📅 TIL (Today I Learned) - 2026.01.28 (수)

### 1. 오늘의 목표

- API 에러 응답 구조 리팩토링 및 효율적인 HTTP 상태 코드 설계 전략 수립

### 2. 진행 내용

- **HTTP 응답 상태 코드 설계 고민**
  - 기존 에러 처리를 `400(Client Error)`이나 `500(Server Error)` 대신, 모든 응답을 `200 OK`로 전달하고 바디(Body) 내의 커스텀 코드로 구분하는 방식을 검토함.
- **현업 사례 및 표준 방식 리서치**
  - **표준 방식 (4xx, 5xx):** 대부분의 REST API 현업 표준으로, 인프라 계층(로드밸런서, API 게이트웨이, 모니터링 도구)에서 에러 여부를 즉시 감지할 수 있는 장점이 있음.
  - **통합 200 방식:** 카카오페이, 토스 등 대규모 결제 시스템에서 주로 사용함. 비즈니스 로직의 복잡도가 매우 높거나, 네트워크 장비의 간섭을 피해야 하는 특수한 금융 결제 환경에서 활용됨을 확인.
- **리팩토링 방향 확정**
  - 우리 프로젝트는 RESTful한 규약을 준수하는 것이 유지보수와 협업에 유리하다고 판단하여, HTTP 표준 상태 코드(`400`, `401`, `403`, `404`, `500` 등)를 적극 활용하는 방향으로 결정함.

### 3. 배운 점 (Insights)

- **인프라와의 협업 고려**
  - 응답 코드를 표준에 맞게 내보내야 로깅 도구나 모니터링 시스템이 "에러 발생"을 자동으로 인지하고 알람을 보낼 수 있다는 점을 배움. 모든 것을 `200`으로 덮으면 인프라 레벨에서의 관제 기능을 상실할 수 있음.
- **도메인 특성에 따른 선택**
  - 금융권이나 결제 시스템이 왜 `200`을 쓰는지(비즈니스 오류와 시스템 오류의 엄격한 분리 등) 이해하게 되었고, 기술 선택에는 정답보다 '우리 서비스의 성격'에 맞는 최적안을 찾는 것이 중요함을 깨달음.
- **직관적인 API 설계**
  - API 사용자가 응답 헤더만 보고도 요청의 성공/실패 여부를 바로 알 수 있도록 설계하는 것이 가장 직관적이고 효율적인 방식임을 확신함.

### 4. 다음 단계

- **이력서 API 연동:** 정립된 에러 응답 규격을 바탕으로 이력서 상세 조회 및 저장 API 연동 작업 착수.
